# Owner onboarding and workspace pairing

**Status: implemented in source; provider-side steps remain manual and unverified on a live account.** This guide describes the customer-owned flow added for the Flutter app and the Cloudflare Worker backend in [cloudflare/](../cloudflare/README.md).

## What each business owns

Every workspace is an isolated deployment in the owner's own Cloudflare account: one Worker, one D1 database, one private R2 bucket. The mobile app never talks to a developer-operated backend and never stores Cloudflare credentials.

## Owner journey in the app

1. First launch shows the workspace gate: **Buat atau gabung workspace**.
2. **Create path:** the owner enters a one-time setup token generated by themselves (password manager or offline generator), sees its SHA-256 digest in the app, opens the Cloudflare Deploy link (copied to clipboard when no browser opener is wired), and completes Cloudflare sign-in, GitHub connection, resource provisioning, and deployment in the browser.
3. The owner adds the digest as Worker secret `OWNER_SETUP_TOKEN_SHA256` (Dashboard → Worker → Settings → Variables and Secrets, or the deploy form if the account UI offers secret input; the deploy-form prompt is **not verified**).
4. Back in the app, the owner pastes the deployed `workers.dev` HTTPS origin, verifies it, and claims the workspace with the raw setup token plus owner name/username/password/workspace name. The Worker checks the token digest, creates exactly one owner atomically, marks the workspace claimed in D1, and returns a session.
5. The app stores only origin, workspace id, and name in device secure storage; the raw setup token and password are cleared from memory after the attempt.
6. **Join path:** employees or extra devices scan the workspace QR (origin + id + name only), confirm the destination, and sign in with accounts created by the owner.

## Verification rules enforced by the app

- Origins must be HTTPS public DNS hosts: no credentials, ports, paths, queries, fragments, localhost, `.local`, or IP literals.
- `GET /v1/workspace` must return exactly `{id,name,ready}`; redirects are rejected.
- Pairing and switching require the server-reported workspace id to match the scanned or stored value.
- Login and all data requests fail closed until a workspace is verified **and** claimed (`ready: true`).
- Pending submissions stay scoped to origin + workspace id + user, so a request can never replay into another business.

## External prerequisites (manual, provider-side)

| Step | Owner action | Verified here |
| --- | --- | --- |
| Cloudflare account | Sign in during Deploy flow | No |
| GitHub/GitLab account | Connect repo source for Deploy button; template must be public | No |
| Deploy button provisioning | Accept Worker, new D1, new private R2 | Docs only |
| R2 activation | Complete subscription/checkout prompt if shown | No |
| Setup digest secret | Add `OWNER_SETUP_TOKEN_SHA256` after first deploy | No |
| D1 migrations | `predeploy` runs `wrangler d1 migrations apply DB --remote` during deploy | Local dry-run only |
| Custom domain (optional) | Configure after workers.dev URL works | No |

The Deploy button's automatic resource provisioning is documented by Cloudflare, but this repository has not executed a live customer deployment. If the deploy form does not accept the digest secret, the documented fallback is the Worker dashboard secret editor after the first deploy; owner setup stays disabled (503) until the digest exists.

## Failure and recovery behavior

- Missing digest: setup endpoint returns 503 `setup_unavailable`; login for existing users still works.
- Wrong token: 401 `invalid_setup_token`; no owner created.
- Second claim or replay: 409 `workspace_claimed`; the app tells the owner to sign in instead.
- Lost claim response: the workspace reports `ready: true`; the owner signs in with the credentials they created. The one-time token is never reused.
- Restoring a pre-claim D1 backup restores the unclaimed state; retain claim markers and rotate the setup token after any restore.

## Automatic setup (beta)

When the app is built with `--dart-define=CLOUDFLARE_OAUTH_CLIENT_ID=<id>` and `--dart-define=CLOUDFLARE_OAUTH_SCOPES=<comma separated scope ids>`, onboarding shows **Setup otomatis**: the app opens Cloudflare OAuth (PKCE, redirect `absensi-bon://oauth`), then provisions everything through the Cloudflare REST API in the owner's account: D1 database, private R2 bucket, schema migrations, Worker upload from the bundled asset, the `OWNER_SETUP_TOKEN_SHA256` secret (digest of an app-generated one-time token), and the workers.dev route. The owner then completes the normal claim form with the pre-filled token. Regenerate the embedded bundle with `npm run bundle:app` in [cloudflare/](../cloudflare/package.json) whenever the Worker or migrations change.

Remaining manual gates even in automatic mode: one-time OAuth client registration by the developer (redirect URI `absensi-bon://oauth`, scopes for D1 Write, Workers R2 Storage Write, Workers Scripts Write, Account Settings Read); owner account signup and consent screen; R2 subscription/payment method activation if the account has not enabled R2 (the app surfaces this as an actionable error).

## Employee onboarding

Employees install the same app, scan the owner's workspace QR or enter the origin manually, confirm the destination, and sign in. The owner creates and deactivates employee accounts in the Karyawan tab; there is no public signup.
